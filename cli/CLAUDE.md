# CLAUDE.md - cli/

`checkoutpage`, the merchant CLI for the Checkout Page seller API. A standalone Rust crate
(`checkoutpage-cli`, binary `checkoutpage`), edition 2024, toolchain pinned by
`rust-toolchain.toml`. User docs are in [README.md](README.md).

## Commands

```bash
cargo build
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test                     # unit + integration, a few seconds
cargo test --test resources    # one integration file
```

CI: `.github/workflows/test-cli.yml` runs fmt, clippy and tests on ubuntu, macos and windows for
changes under `cli/`. Keep the crate building on Windows: Unix-only code (file modes) goes behind
`#[cfg(unix)]` with a `#[cfg(not(unix))]` fallback.

## Layout

- `src/api/` - the HTTP client, with no CLI concerns, so it can become a standalone Rust SDK
  crate. `Client` (bearer auth, query building, cursor pagination), `ApiError` (mirrors the JS
  SDK's error classes), `oauth` (register, authorize URL, token, refresh, issue-api-key,
  revoke) and `pkce`.
- `src/cli.rs` - clap definitions. `src/app.rs` - credential and base URL precedence, OAuth key
  refresh, `--test`/`--live` mapping, exit codes.
- `src/commands/` - one module per command group. `resources.rs` holds a column spec per
  resource; table, CSV and `get` views all come from it.
- `src/config.rs` (profiles in `config.toml`, 0600), `src/callback.rs` (loopback login
  redirect), `src/money.rs` (minor units, zero-decimal currencies).
- `tests/` - integration tests running the real binary with `CHECKOUTPAGE_CONFIG_DIR` in a
  tempdir: `resources.rs` and `auth.rs` (the test plays the browser), with helpers in
  `tests/common/`.

## Conventions

- The OpenAPI spec (`../spec/openapi.json`) is the source of truth for paths, query params and
  shapes. List paths keep the spec's trailing slash (`/v1/coupons/`), like the JS SDK.
- Single-object responses come wrapped in `{ "data": ... }`; use `api::unwrap_data`, which also
  accepts a bare object.
- Print through `output::out` / `output::err`, not `println!`, so a closed pipe exits quietly.
- Never print a full API key; use `util::mask_key`.
- No em dashes in user-facing strings (help text, messages, README).

## Releasing

Releases are built and published by [dist](https://github.com/axodotdev/cargo-dist) (formerly
cargo-dist). A release is a `checkoutpage-cli-v<version>` tag; dist names tags after the Cargo
package, not the binary.

- `dist-workspace.toml` at the repo root holds the dist config: targets, installers, the
  Homebrew tap, `publish-jobs` and `tag-namespace = "checkoutpage-cli"`. It lives at the root,
  not in `cli/`, because dist writes its workflow next to the workspace it finds, and GitHub
  only runs workflows from the root `.github/workflows/`. `members = ["cargo:cli"]` points it
  at this crate. Package settings (`formula`, `npm-scope`, `npm-package`, `dist = true`, which
  is needed because of `publish = false`) are under `[package.metadata.dist]` in `Cargo.toml`.
- `.github/workflows/checkoutpage-cli-release.yml` is generated by `dist generate` from that
  config. Never edit it by hand: change the config and regenerate. `tag-namespace` limits it to
  tags starting `checkoutpage-cli`, so `js-v*` tags don't start it. On pull requests it only runs
  `dist plan`.
- `.github/workflows/publish-cli.yml` ("Release CLI") is the hand-run entry point. It bumps
  `version` in `Cargo.toml` and `Cargo.lock`, runs the tests, commits
  `chore(cli): release <version>` to main and pushes the `checkoutpage-cli-v<version>` tag.
- A tag pushed with the default `GITHUB_TOKEN` does not start other workflows, so the Release
  CLI workflow checks out and pushes with the `RELEASE_TOKEN` secret instead. Without it the
  tag would land and nothing would build.

Targets: `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`,
`aarch64-unknown-linux-gnu`, `x86_64-unknown-linux-musl` (static, fine because reqwest uses
rustls, not OpenSSL) and `x86_64-pc-windows-msvc`. Installers: shell, PowerShell, Homebrew
(`checkout-page/homebrew-tap`, formula `checkoutpage`) and npm (`@checkoutpage/cli`).
crates.io publishing is off (`publish = false`); the package metadata it needs is already in
`Cargo.toml`.

### One-time setup

1. Create the public repo `checkout-page/homebrew-tap` with a README. dist manages
   `Formula/checkoutpage.rb` in it.
2. Create a fine-grained GitHub token with Contents read and write on
   `checkout-page/homebrew-tap`, and add it to this repo's Actions secrets as
   `HOMEBREW_TAP_TOKEN`.
3. Create an npm granular access token with read and write on the `@checkoutpage` scope (the
   npm organization already publishes `@checkoutpage/sdk`), and add it as `NPM_TOKEN`.
4. Create a fine-grained GitHub token (or a GitHub App token) with Contents read and write on
   `checkout-page/checkoutpage-api-sdk`, and add it as `RELEASE_TOKEN`. Its owner must be
   allowed to push to `main` if `main` is protected.

Tokens expire: when a release fails at the Homebrew, npm or push step, renew that secret first.

### Each release

1. Merge everything for the release to main, with `cargo test` green.
2. Actions, Release CLI, Run workflow, enter the version without a `v` (`0.2.0`).
3. Watch the `Release` run that the tag starts (`checkoutpage-cli-release.yml`). It builds
   every target, creates the GitHub Release with the archives and installers, then publishes
   the Homebrew formula and the npm package. Prerelease versions (`0.2.0-rc.1`) get a GitHub
   Release but skip Homebrew and npm.
4. Check `brew install checkout-page/tap/checkoutpage` and `npm install -g @checkoutpage/cli`
   install the new version.

To upgrade dist itself: install the new version, run `dist init` from the repo root (it keeps
the config and updates `cargo-dist-version`), then `dist generate`, and commit both files. Check
locally with `dist plan` and `dist build --artifacts=local --target=<host>` from the repo root.
